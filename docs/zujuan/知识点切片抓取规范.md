# 知识点切片抓取规范：只抓叶子 + 翻页翻不完时怎么切

## 0. 这份文档接着哪份、边界在哪

承接《知识点树抓取规范.md》——那份讲怎么拿到"要抓哪些知识点"的清单；这份讲**拿到清单之后，具体怎么把每个知识点底下的题抓全**：只抓叶子节点、翻页翻不完时怎么用筛选条件把一个知识点切小。

**不包含**：题干怎么从卡片解析出字段（《题干解析规范.md》）、解析结果怎么写进数据库（《题干入库规范.md》）、知识点树本身怎么抓（《知识点树抓取规范.md》）。也**不包含**随机打乱翻页顺序这类防风控的辅助手段——那是一个默认关闭、本项目自己都还没在真实场景里验证过效果的防御性功能，不属于核心抓取策略，这份文档不涉及。

---

## 1. 只抓叶子节点

**为什么**：一个知识点的列表页，包含的是**它自己 + 它全部子孙节点**的题。比如"相反数"这个知识点，页面上写着"共计 24003 道"，但这些题**一道都不会**直接标"相反数"这个知识点，站点给题打的标签用的是更细的三个子节点（"相反数的定义"/"化简多重符号"/"相反数的应用"）。如果父节点和子节点都抓一遍，子节点那批题会被重复翻页两次。

**判断方法**：一个知识点节点如果没有任何子节点（子节点数为 0），就是叶子——这个值就是《知识点树抓取规范.md》里压平算法算出来的 `child_count`，判断条件是 `child_count == 0`。

**结论**：遍历知识点树时，只把 `child_count == 0` 的节点放进"要抓"的清单里，其它节点（哪怕它页面上写着几万道题、看起来很吓人）直接跳过，不打开它的列表页。一道题会挂多个知识点（最多见过 10 个）属于正常的多对多关系，不是重复采集，不用去重。

---

## 2. 列表页 URL 结构

```
https://zujuan.xkw.com/{学段前缀}/zsd{知识点ID}/{筛选条件段…}o{排序码}p{页码}/
```

学段前缀：初中 `czsx`，高中 `gzsx`。

筛选条件段是若干段拼在一起、没有分隔符，比如"题型=单选题 难度=困难"是 `qt1101d3`；**这份文档要用到的几个筛选维度顺序是**：题型 → 难度 → 年份（→ 排序+页码）。第 1 页可以不写页码（`o2/` 等价于 `o2p1/`），第 N 页写成 `o2p{N}/`。排序码固定用"最新"（`o2`）即可（对应 `order=latest`）。

页面上有一处固定会显示"**共计 N 道试题**"（HTML 里对应 `<em class="ques-sum" id="questioncount">` 这个元素），**带筛选条件时显示的就是这一片筛选结果的数**——这是整份文档要用到的核心依据：判断"这个知识点/这一片翻页能不能翻完"、以及切片时"往下切要切到什么程度"，全靠读这一个数字。读不到就当"不知道"处理，不要当成 0。

## 3. 翻页硬顶：第 999 页 = 9990 道

**实测结论**：这个站点的列表页翻页最多只能翻到第 999 页。从第 1000 页开始，服务端**不会报错、也不会返回空页**，而是把第 999 页的内容原样重复返回给你——页码看起来还在往前走，内容却是同一批题。

**后果**：如果不做检测，翻页循环会一直跑到设定的页数上限，反反复复处理同样 10 道题，表现是"程序一直在跑，但入库数量不再增加"——这是最难发现的一类故障，因为它不报任何错误。

**检测方法**：每翻完一页，把这一页 10 道题的题目 ID 列表和上一页的题目 ID 列表比较一下——**完全相同**就说明撞到了这个硬顶，必须立刻停止翻页，不要再往后翻了。

**换算成"道数"的上限**：一页 10 道，999 页 = **9990 道**。也就是说，**任何一个筛选条件组合出来的 URL，最多只能通过翻页拿到 9990 道题**，不管这一片实际上有多少道。

**另一种"翻到头了"的正常情况，不要和撞硬顶搞混**：翻到某一页发现没有任何题目卡片了，这是正常的"已经翻到底"（这个知识点/这一片的题就这么多），不是撞硬顶——用"这一页有没有卡片"和"这一页和上一页内容是不是完全重复"来区分这两种情况，处置完全不同（翻到底了就是正常结束；撞硬顶了说明这一片还有拿不到的题，需要靠第 4 节的切片来解决）。

**一个容易漏掉的边界情况**：如果翻到某一页，页面上连"共计 N 道试题"这个数字都读不到了（正常情况下，哪怕这一页恰好没有卡片，这个数字也应该还在），这说明打开的可能根本不是一个正常的列表页（比如被拦截、或者页面结构变了）——这种情况下**不要**当成"翻完了"来处理，应该原样保留"还没翻完"的状态，下次再从这一页重试。把它误判成"翻完了"的代价是这个知识点后面的题永远不会再被采集。

## 4. 超过 9990 道怎么办：按筛选条件切片

### 4.1 核心原理

翻页硬顶是**针对每一个具体的 URL 单独计算的**。给一个知识点加上一个筛选条件（比如"只看单选题"），就得到了一个新的 URL，这个新 URL 有它自己独立的 999 页 / 9990 道硬顶。所以只要把一个题量很大的知识点，用筛选条件切成几个足够小的片，每一片单独翻页就都能翻完——这就是切片能绕开硬顶的全部原理。

打开一个知识点时先看它的"共计 N 道"：**N ≤ 9990**，直接翻页翻完，不需要切片；**N > 9990**，必须切片，而且应该在读到这个数字的第一时间就决定改走切片，不要傻等真的翻到第 999 页才发现翻不完——那样等于白白翻了几千页才意识到问题。

### 4.2 切片维度，固定顺序：题型 → 难度 → 解答题子题型 → 年份

```
第 1 维  题型     5 档（单选/多选/填空/解答/判断）
第 2 维  难度     3 档（容易/适中/困难）
第 3 维  解答题子题型  5 档（计算题/作图题/应用题/证明题/问答题）—— ★只有"解答题"这个题型才有这一维
第 4 维  年份     8 档（2020~2026 逐年 + "更早以前"）
```

**为什么是这个顺序**：

- 优先用**分得更细、而且是严格划分（不重叠）**的维度——题型 5 档、难度 3 档，先切完这两维，大部分知识点的每一片就已经落在 9990 道以内了，用不到后面两维
- 解答题子题型**只在"题型=解答题"这个条件下才存在**——单选题、填空题、多选题、判断题底下都没有这一档可选。所以往下钻的时候，如果当前这个维度在当前的筛选条件下没有任何可选值，要**跳过去找下一个维度**，不能因为"这一维不存在"就判定"切不动了、只能放弃"
- **年份这一维排最后，是因为它的档之间是重叠的，不是严格划分**：一道题可能同时出现在好几个不同年份的试卷里（题目和试卷本来就是多对多关系），按年份切出来的几片题量加总，会比这个知识点/这一片的实际题量多出约 1.6 倍。所以能用前三维切开就不要动年份这一维；真用到了，也要清楚"年份片之间有重叠"这个事实，不是数据错了

四个维度都是**在当前筛选条件下**才能确定要不要用、有哪些取值——比如"解答题子题型"要先知道"题型=解答题"这个前提才存在，"年份"和前面几维无关，任何时候都可以用。

### 4.3 按需下钻，不预先展开

不要一次性把所有维度组合都列出来再挨个去试（题型 5 档 × 难度 3 档 × 子题型 5 档 × 年份 8 档，展开有几百种组合，绝大多数知识点根本用不到这么多）。正确做法是**每切一层看一眼这一片的"共计 N 道"，够用了就直接翻页，不够用才再往下切一维**：

```
处理一个知识点/一片（带着当前的筛选条件，可能是空的）：

    打开这一片的第 1 页，读"共计 N 道试题"

    如果 N ≤ 9990：
        正常翻页翻完这一片（用第 3 节的硬顶检测保护）
        结束

    否则（N > 9990，翻页翻不完）：
        从当前深度往后找第一个"在这个筛选条件下有可选值"的维度
        （比如筛选条件已经是"题型=单选题"了，就跳过"解答题子题型"这一维，
          去找下一个——年份）

        如果四个维度都试过了，找不到还能用的维度：
            → 这一片切到底了还是超过硬顶，标记为"切到底了还是超"，
              不再自动重试（第 4.4 节）
            结束

        否则，拿到这个维度的全部取值（比如题型的 5 档）：
            for 每个取值：
                在当前筛选条件上再叠加"这一维 = 这个取值"，得到一个更细的筛选条件
                递归处理这个更细的筛选条件（回到本流程最开头，"打开这一片的第 1 页"）
```

这个流程从"这个知识点，不带任何筛选条件"开始递归调用。

### 4.4 切到底了还是超怎么办

四个维度（题型 → 难度 → 解答题子题型 → 年份）都用完了，某一片仍然超过 9990 道——这种情况**不要**再自动重试，标记成一个终止状态（"切到底了还是超"），并且记下这一片还差多少道题拿不到。这种情况很少见，出现了应该是人去看一眼、判断要不要再加一个新的筛选维度（比如"来源类型"或"年级"，这两个站点本身也支持筛选，只是目前没有用在这条切片逻辑里）。

### 4.5 切片是否盖全了整个知识点，值得对一次账

把各片各自的"共计 N 道"加起来，理论上应该约等于（题型和难度这两维是严格划分，加起来应该正好等于；用到年份维度的话前面已经说过会多出约 1.6 倍，属于正常重叠）这个知识点整体的"共计 N 道"。如果明显对不上（比如差出几百道），大概率是站点新增了一种这里没覆盖到的题型，值得留意，不然会出现"进度显示采完了，但实际比站点少了一截"却查不出原因的情况。

## 5. 进度记录：一个知识点、一片各对应一行

按知识点抓取是个需要断点续采的长过程（一个知识点可能要翻几十页，切片之后一个知识点可能对应几十片），所以每处理完一页/一片都要记一次进度，方便中断后接着采，而不是从头再来。

### 5.1 表结构

**知识点整体的进度**——挂在《知识点树抓取规范.md》里 `knowledge_tree` 表的进度列上（那份文档已经列出了这些列的存在，这里只重申会用到的几个）：

| 列 | 说明 |
|---|---|
| `scrape_status` | `none`没采过 / `partial`采了一半 / `slicing`题太多，已经改成按筛选条件切片 / `done`采完了 / `capped`切到底仍然超过硬顶 / `empty`站点说这里没题 |
| `site_total` | 这个知识点"共计"多少道（不带任何筛选条件） |
| `collected` | 库里这个知识点（含全部子孙，虽然只抓叶子，但父节点的这个数应该等于子孙加总）目前有多少道 |
| `last_page` | 顺序翻页时，上次翻到第几页——不切片时断点续采靠它，下次从 `last_page + 1` 开始 |

一个知识点一旦决定要切片（`scrape_status = 'slicing'`），`last_page` 这一列就不再更新了——切开之后，每一片各有各的页码，一个数字表达不了，进度要看下面这张表。

**每一片的进度**——单独一张表：

```sql
CREATE TABLE IF NOT EXISTS knowledge_slice (
    knowledge_id    VARCHAR(32)  NOT NULL,   -- 属于哪个知识点
    slice_key       VARCHAR(32)  NOT NULL,   -- 这一片的筛选条件标识，见 5.2 节

    dim             VARCHAR(16),             -- 这一片是按哪一维切出来的：qtype/difficulty/sub_type/year
    slice_name      VARCHAR(64),             -- 这一片的人话名字，如"单选题·困难"
    depth           INT DEFAULT 1,           -- 切了几层：1=只切了第一维，2=切了两维，以此类推

    scrape_status   VARCHAR(16) DEFAULT 'none',  -- 取值和 knowledge_tree.scrape_status 一样
    site_total      INT,                     -- 这一片"共计"多少道
    collected       INT DEFAULT 0,           -- 库里这一片目前有多少道
    last_page       INT DEFAULT 0,           -- 这一片翻到第几页了

    note            VARCHAR(255),
    scraped_at      VARCHAR(32),

    PRIMARY KEY (knowledge_id, slice_key),
    KEY idx_ks_todo (knowledge_id, scrape_status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

### 5.2 `slice_key`：既是主键，也能直接拼回 URL

`slice_key` 是**各维度的筛选码首尾相接**，和这一片对应的 URL 筛选段完全一样：

```
{"题型": 单选题}                       → "t1"      （对应 URL 段 qt1101，见下面的码表）
{"题型": 单选题, "难度": 困难}          → "t1d3"
{"题型": 解答题, "子题型": 问答题, "难度": 困难} → "t4d3s5"
{"题型": 解答题, "子题型": 问答题, "难度": 困难, "年份": 2025} → "t4d3s5y2025"
```

拼接顺序**固定按第 4.2 节的维度顺序**（题型 → 难度 → 子题型 → 年份），不是按填写顺序或字母顺序——这样同一组筛选条件永远得到同一个 `slice_key`，断点续采时才能找到上次写的那一行，不会因为顺序不同而查不到、又从头切一遍。

各维度对外用的短码，和拼 URL 用的真实站点码是两套（短码只在 `slice_key` 里用，拼 URL 时要翻译成真实站点码）：

| 维度 | 短码 → 站点 URL 码（初中） |
|---|---|
| 题型 | `t1`→单选题(1101) `t2`→多选题(1104) `t3`→填空题(1102) `t4`→解答题(1103) `t5`→判断题(1105) |
| 难度 | `d1`→容易 `d2`→适中 `d3`→困难（URL 段直接就是 `d1`/`d2`/`d3`，和这里的短码一样） |
| 解答题子题型 | `s1`→计算题(01) `s2`→作图题(02) `s3`→应用题(03) `s4`→证明题(04) `s5`→问答题(05)，拼 URL 时是接在题型码后面的两位，如 `qt1103` + `05` = `qt110305` |
| 年份 | `y2020`~`y2026`（对应 URL 段 `y2020`~`y2026`），以及 `y-1`（"更早以前"，对应 URL 段 `y-1`，含义是"比 2020 还早"，是一个范围不是某一年） |

（高中的题型码和初中不是同一套，这份文档只给初中的码表；如果要抓高中，第一步要重新核对一遍这张表。）

### 5.3 写入逻辑

**每翻完一页立刻写一次进度并提交**，不要攒到一整片/一整个知识点都翻完才写——半路中断（网络问题、程序被杀）最多只丢当前正在翻的这一页，不会丢掉已经翻完的部分。

```
翻完一页之后：
    如果这个知识点还没有在切片模式（还没决定要不要切）：
        UPDATE knowledge_tree
           SET scrape_status='partial', last_page=<刚翻完的页码>, site_total=<这个数>
         WHERE knowledge_id = <这个知识点>
    否则（正在切某一片）：
        INSERT INTO knowledge_slice (knowledge_id, slice_key, dim, slice_name, depth,
                                      scrape_status, last_page, site_total)
             VALUES (..., 'partial', <刚翻完的页码>, <这个数>, ...)
        ON DUPLICATE KEY UPDATE
             scrape_status='partial', last_page=<刚翻完的页码>, site_total=<这个数>
             -- 或者：先按 (knowledge_id, slice_key) 查一次，
             --      存在就 UPDATE，不存在就 INSERT，效果一样

    commit
```

一个知识点翻到底（正常结束，见第 3 节）之后，把 `scrape_status` 写成 `done`；发现"共计 N 道"超过 9990（第 4.1 节）之后，把 `scrape_status` 写成 `slicing` 并开始按第 4.3 节的流程往下切；某一片按四个维度都切过了仍然超（第 4.4 节），把这一片的 `scrape_status` 写成"切到底了还是超"这个终止值；某一片下面的全部子片都处理完了，把这一片自己的 `scrape_status` 汇总成"这一片是不是完全采完了"（子片全部正常结束且没有任何一片是"切到底还超" → 这一片算采完；子片里只要有一个是"切到底还超" → 这一片也标成"切到底还超"，让人知道这个知识点确实有一部分题拿不全）。

## 6. 完整示例

以"相反数"这个知识点为例（真实数据，2026-08 实测）：

```
zsd4697「相反数」，共计 24003 道 —— 超过 9990，必须切片

按题型切成 5 片：
  qt1101（单选题）  共计 10707 道 —— 还是超过 9990，这一片要再往下切
  qt1104（多选题）  共计    36 道 —— 够了，直接翻页翻完
  qt1102（填空题）  共计  ????  道 —— 按实际数处理
  qt1103（解答题）  共计  ????  道
  qt1105（判断题）  共计  ????  道

「单选题」这一片按难度再切成 3 片：
  qt1101d1（容易）  共计  9383 道 —— 够了，直接翻页翻完
  qt1101d2（适中）  共计  1296 道 —— 够了，直接翻页翻完
  qt1101d3（困难）  共计    28 道 —— 够了，直接翻页翻完

  9383 + 1296 + 28 = 10707，正好等于父片"单选题"的总数，一道不差
  （题型→难度是严格划分，加总应该完全对得上；如果用到了年份维度，
    加总会明显大于父片，那是正常的重叠，不是算错了）
```

对应的 `slice_key`：单选题这一片是 `t1`，单选题·容易这一片是 `t1d1`，以此类推。`knowledge_slice` 表里会有 `t1`（`scrape_status=slicing`，因为它自己还超，被再往下切了）、`t1d1`/`t1d2`/`t1d3`（这三片各自 `scrape_status=done`）等好几行，`knowledge_id` 都是 `zsd4697`。
