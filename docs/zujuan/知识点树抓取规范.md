# 知识点树抓取规范：数据源、解析算法、入库

## 0. 这份文档是什么、和前两份的关系

《题干解析规范.md》《题干入库规范.md》讲的是"抓一道题"；这份讲的是更前置的一件事——**知道要抓哪些知识点**。本项目按知识点遍历采集（每个知识点对应一个列表页 URL），这份清单和每个知识点的名称/层级/父子关系，就来自"知识点树"。

**这棵树和题干抓取是两条独立的线**：题干抓取需要先有这份清单才能决定"打开哪些 URL"；反过来，题干解析出来的 `question_knowledge.knowledge_id` 要能在这棵树里查到对应节点（对得上名字、对得上层级），两边共用同一套 ID 空间，所以这份文档单独写清楚。

**不包含**：

| 不包含 | 为什么 |
|---|---|
| 教材章节树（`textbook`/`textbook_chapter`，URL 段 `zj<id>`） | 性质完全不同的另一棵树——分版本分册、没有免费静态数据源、必须用浏览器过 WAF 才能抓，和这里讲的知识点树不是一回事，不要混 |
| 知识点的**采集进度**（是否采完、采到第几页、这个知识点下有多少道题…） | 这些是"抓题干"那条线在跑的过程中自己维护的状态，不属于"知识点树"这份静态数据本身。第 3 节会列出这些列的存在，但明确标注不归这次任务管 |

**只需要产出一样东西**：`knowledge_tree` 表里"树结构"相关的那些行/列（节点 ID、名称、层级、父子关系、路径）。

## 1. 数据源：免费静态 JSON，不需要浏览器、不需要登录

```
https://static.zxxk.com/zujuan/tree/lk_{bank_id}.json
```

这个 CDN（`static.zxxk.com`）和抓题目用的主站（`zujuan.xkw.com`）不是同一个域，**这个域没有挂 WAF**，普通 HTTP GET 直接拿到 200 和完整 JSON，不需要走浏览器、不需要 cookie、不需要登录态。带一个常规浏览器 User-Agent 请求头即可（不带也大概率能行，带上更保险）。

`bank_id` 是学科编号，几个已知取值（都是初中）：

| `bank_id` | 学科 |
|---|---|
| 1 | 初中语文 |
| **2** | **初中数学**（本项目默认用这个） |
| 3 | 初中英语 |
| 4 | 初中物理 |
| 5 | 初中化学 |
| 6 | 初中生物 |
| 7 | 初中政治 |

初中数学（`bank_id=2`）这棵树：**1696 个节点，最深 5 层**，整棵树大小约 280KB。

**★ 这棵树不分年级、不分教材版本 ★**——顶层是按数学主题分类的（数与式 / 方程与不等式 / 函数 / 图形的性质 / 图形的变化 / 统计与概率 / 观察猜想与证明 / 实践与应用 / 向量的运算 / 五四制小学衔接 / 数学竞赛），不会看到"七年级""人教版"这类节点。分年级分版本的是教材章节树（不在这次任务范围内）。

## 2. JSON 结构与压平算法

原始 JSON 是一棵嵌套树，根节点长这样（字段是站点原生给的，不是本项目定义的）：

```json
{
  "id": "0", "title": "初中数学综合库", "treeType": 1, "isKnowledge": 1,
  "children": [
    {
      "id": "4685", "title": "数与式", "bankId": 2, "isKnowledge": 1,
      "href": "/czsx/zsd4685",
      "children": [
        {"id": "4687", "title": "有理数", "isKnowledge": 1, "href": "/czsx/zsd4687",
         "children": [
           {"id": "4700", "title": "相反数", "isKnowledge": 1, "href": "/czsx/zsd4700",
            "children": [ /* 更深一层，或者是空数组表示叶子 */ ]}
         ]}
      ]
    }
  ]
}
```

关键字段：`id`（纯数字字符串）、`title`（节点名称）、`bankId`（学科编号，通常只在顶层附近出现，子节点可能没有，取不到就沿用调用时传入的 `bank_id`）、`href`（形如 `/czsx/zsd4700`，可能为空）、`isKnowledge`（站点自己的标记，实测全树都是 1）、`children`（子节点数组，空数组或不存在都表示这是叶子节点）。

**压平算法**：从根节点开始做一次深度优先遍历（前序），把每个节点转成一条扁平记录，同时携带层级、父节点、路径信息：

```
walk(node, level, 标题链, 父节点原始id, 在同级中的序号):
    raw_id = str(node.id)
    如果 raw_id 是空的：跳过这个节点（不递归它的子节点）

    title = node.title
    新的标题链 = 标题链 + [title]
    children = node.children（不存在就当空数组）

    输出一条记录：
        knowledge_id  = "zsd" + raw_id          ★见下面的重点说明
        node_id       = raw_id                  （不带前缀的原始数字）
        bank_id       = node.bankId，取不到就用调用时传入的 bank_id
        title         = title
        parent_id     = 父节点原始id 非空 ? ("zsd" + 父节点原始id) : null
        level         = level（根节点 level=0）
        path          = 用 " / " 连接"新的标题链"里所有非空的标题
        href          = node.href，没有就 null
        is_knowledge  = int(node.isKnowledge)，取不到当 0
        child_count   = len(children)
        sort_ord      = 在同级中的序号（从 0 开始，按 JSON 里出现的顺序）

    对 children 里每个子节点 c，按下标 i：
        递归 walk(c, level+1, 新的标题链, raw_id, i)

从 walk(根节点, level=0, [], 父id=null, 0) 开始
```

**child_count == 0 就是叶子节点**——这是真正用来给题目打标签的那一层，本项目采集只走叶子（父节点页面本身就包含全部子孙的题，采父节点会把子节点的题重复采一遍）。压平这一步只需要算出 `child_count`，"是不是叶子"这个判断留给采集那条线自己处理，不属于这份文档范围。

### ★ 最容易踩的坑：`knowledge_id` 必须带 `zsd` 前缀 ★

JSON 里的 `id` 是纯数字（`"4700"`），但**题目那条线存的知识点 ID 是带 `zsd` 前缀的**（`question_knowledge.knowledge_id` = `"zsd4700"`，这个前缀是从题目卡片链接 `/czsx/zsd4700` 里抠出来的，见《题干解析规范.md》2.9 节）。

如果知识点树这边存的是不带前缀的纯数字 `"4700"`，两边 `JOIN` 的时候会**完全查不到任何匹配，但不会报错**——查询结果只是安静地变成空，很容易被误以为"这个知识点没有题"。所以压平时必须统一：`knowledge_id`/`parent_id` 都要拼上 `"zsd"` 前缀，原始的纯数字额外存一份到 `node_id` 列（万一以后要用原始 ID 去拼别的 URL）。

## 3. 表结构

`knowledge_tree` 也是一张共享表——除了树结构本身，题目采集那条线会在上面挂一批"这个知识点采到第几页了"之类的进度列。和《题干入库规范.md》里 `questions` 表的处理原则一样：**只碰这次任务负责的列，进度列列出来只是让你知道它们存在，不要在写入语句里出现它们**。

```sql
CREATE TABLE IF NOT EXISTS knowledge_tree (
    -- ================================================================
    -- 第一组：这次任务负责的列（树结构本身）
    -- ================================================================
    knowledge_id    VARCHAR(32)  NOT NULL,   -- 带 zsd 前缀，如 "zsd4700"
    node_id         VARCHAR(32),             -- 不带前缀的原始数字 ID，如 "4700"
    bank_id         VARCHAR(16),             -- 学科编号，初中数学=2
    title           VARCHAR(128),            -- 知识点名称
    parent_id       VARCHAR(32),             -- 父节点 knowledge_id（同样带 zsd 前缀），根节点为空
    level           INT,                     -- 层级，根=0
    path            VARCHAR(512),            -- 从根到本节点的完整路径，" / " 连接
    href            VARCHAR(128),            -- 站点链接，如 /czsx/zsd4700
    is_knowledge    TINYINT,                 -- 站点原样给的标记，实测全树都是 1
    child_count     INT,                     -- 直接子节点数，0 表示叶子
    sort_ord        INT,                     -- 同级里的顺序，保持 JSON 原始排列
    updated_at      VARCHAR(32),             -- 这一行最后一次同步的时间戳，自动填

    -- ================================================================
    -- 第二组：题目采集那条线维护的进度列 —— ★不要在这次任务里写它们★
    -- 只是如实列出真实表结构，避免误以为这张表只有上面那些列
    -- ================================================================
    is_leaf         TINYINT DEFAULT 0,
    scrape_status   VARCHAR(16) DEFAULT 'none',
    site_total      INT,
    collected       INT DEFAULT 0,
    last_page       INT DEFAULT 0,
    covered_pages   TEXT,
    scraped_at      VARCHAR(32),
    note            VARCHAR(255),

    PRIMARY KEY (knowledge_id),
    KEY idx_kt_parent (parent_id),
    KEY idx_kt_level (level),
    KEY idx_kt_todo (is_leaf, scrape_status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

第二组这几列，新插入一行知识点时**不用管它们**——建表语句里都带了默认值（`is_leaf`/`collected`/`last_page` 默认 0，`scrape_status` 默认 `'none'`），一条只写第一组列的 `INSERT` 会自动让这些列落到默认值，不需要显式写。**唯一要注意的是更新已存在的行时，SET 子句同样只能出现第一组的列**，原因和《题干入库规范.md》里 `questions` 表的规则完全一样：这些进度列可能已经被题目采集那条线写过实际进度了，一条覆盖式的更新会把进度冲掉。

## 5. 写入逻辑：整棵树当成一份快照，逐行 upsert

和《题干入库规范.md》里"先查再决定插入/更新/跳过"不一样，知识点树的写入更简单：**每次同步就是拿到完整一棵树，逐个节点做"有就更新、没有就插入"**，不用先判断"要不要写"——树本身不大（1696 行），站点难得变一次，直接全量 upsert 一遍成本很低。

```
拉取 + 压平出 nodes（第 2 节的算法，得到 1696 条记录）

for row in nodes:
    如果 row.knowledge_id 是空的：跳过这一条（异常数据，不应该发生）

    尝试 INSERT INTO knowledge_tree (第一组全部列) VALUES (对应的值)
    如果因为主键冲突失败（这一行已经存在）：
        忽略这次插入失败（不是错误，是正常情况）

    执行 UPDATE knowledge_tree
         SET node_id=?, bank_id=?, title=?, parent_id=?, level=?,
             path=?, href=?, is_knowledge=?, child_count=?, sort_ord=?,
             updated_at=?
         WHERE knowledge_id = row.knowledge_id
    # ★ SET 子句只能出现第一组这些列，不要出现 is_leaf/scrape_status/
    #   site_total/collected/last_page/covered_pages/scraped_at/note

处理完全部 1696 条之后统一 commit
```

**为什么是"逐行 upsert"而不是"先删整表再全部插入"**：知识点树被其它表（比如题目和教材章节的关联表）引用着，如果先整表 `DELETE` 再重新插入，在这个空档期内任何引用这些 ID 的查询都会短暂查不到对应的知识点行（"外键悬空"）。逐行 upsert 慢一点，但任何时刻表都是完整、可查询的，不会有这个空档期问题。

**为什么每行是"插入失败就忽略，然后总是再执行一次 UPDATE"，而不是先查一次"存在吗"再决定走哪条分支**：效果上完全等价（判断-插入-判断-更新 vs 插入-忽略失败-更新），但省了一次额外的 SELECT，实现更简单。两种写法你可以按自己技术栈的习惯选，只要最终"存在就更新、不存在就插入"这个语义对就行。

**这次任务全程不需要用到"先查这一行现在的进度状态如何"这类逻辑**——那是题目采集那条线的关注点，和"同步知识点树"这个动作完全独立，不要在这一步夹杂任何进度判断。

## 6. 完整示例

以 JSON 里 `数与式 → 有理数 → 相反数` 这条链路为例：

```json
{"id": "4685", "title": "数与式", "bankId": 2, "href": "/czsx/zsd4685",
 "children": [
   {"id": "4687", "title": "有理数", "href": "/czsx/zsd4687",
    "children": [
      {"id": "4700", "title": "相反数", "href": "/czsx/zsd4700", "children": []}
    ]}
 ]}
```

压平出 3 条记录（假设 `数与式` 的父节点是根节点 `id="0"` 且 `level=0`）：

```
knowledge_id=zsd4685  node_id=4685  parent_id=null      level=1  path="数与式"                 child_count=1
knowledge_id=zsd4687  node_id=4687  parent_id=zsd4685   level=2  path="数与式 / 有理数"          child_count=1
knowledge_id=zsd4700  node_id=4700  parent_id=zsd4687   level=3  path="数与式 / 有理数 / 相反数"  child_count=0   ← 叶子（child_count=0）
```

对应的写入（以 `zsd4700` 这一行为例）：

```sql
INSERT INTO knowledge_tree
    (knowledge_id, node_id, bank_id, title, parent_id, level, path,
     href, is_knowledge, child_count, sort_ord, updated_at)
VALUES
    ('zsd4700', '4700', '2', '相反数', 'zsd4687', 3, '数与式 / 有理数 / 相反数',
     '/czsx/zsd4700', 1, 0, 0, '2026-09-03T10:00:00');
-- 如果这一行已存在（主键冲突），改为：
UPDATE knowledge_tree
   SET node_id='4700', bank_id='2', title='相反数', parent_id='zsd4687',
       level=3, path='数与式 / 有理数 / 相反数', href='/czsx/zsd4700',
       is_knowledge=1, child_count=0, sort_ord=0, updated_at='2026-09-03T10:00:00'
 WHERE knowledge_id = 'zsd4700';
```

## 7. 范围重申

这份文档到"知识点树同步进数据库"为止。**这棵树的用途**——按叶子节点遍历生成题目列表页 URL、断点续采、题太多时按题型/难度切片——都是"抓题干"那条线的事，不在这份文档里；那条线需要的只是这份文档产出的 `knowledge_tree` 表里那份干净的树结构（尤其是 `knowledge_id`/`parent_id`/`child_count`/`href` 这几列），剩下的进度维护它自己负责。
