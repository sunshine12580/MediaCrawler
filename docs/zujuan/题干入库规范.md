# 题干入库规范：解析结果 → 数据库

## 0. 这份文档接着哪份文档、边界在哪

承接《题干解析规范.md》——那份文档讲"HTML 怎么解析成字段",这份讲**拿到解析结果之后怎么写进数据库**：写哪几张表、每个字段对应哪一列、什么情况下该插入/更新/跳过、什么东西绝对不能碰。

**不包含**：字段是怎么从 HTML 解析出来的（看《题干解析规范.md》）、原始 JSONL 文件的格式（同上）、答案/离线渲染/OCR 相关的任何写入逻辑（这些阶段各自有自己的写入函数，这份文档不涉及）。

**前提：`questions` 是一张共享的大表，不是这次任务专属的表**——除了题干，答案抓取、离线 HTML→Markdown 转换、图片 OCR 这几个阶段也会往这同一张表写数据（各自负责不同的列）。这意味着写入的时候**只能碰这次任务负责的那些列，绝对不能用"整行覆盖"的方式写入**，否则会把其它阶段已经写好的数据冲掉——这是这份文档要重点强调的部分。

---

## 1. 涉及三张表

| 表 | 用途 | 这次任务负责的程度 |
|---|---|---|
| `questions` | 一道题一行，题干只是其中一部分列 | 只写题干相关的约 30 列，其余约 30 列（答案、离线渲染产物）**禁止触碰** |
| `question_knowledge` | 一题可能挂多个知识点，多对多关联表 | 完全负责 |
| `question_sources` | 一题可能被多套试卷收录，多对多关联表 | 完全负责 |

## 2. 字符集要求

三张表建表时都必须是 **`utf8mb4`**（不是 `utf8`）。`utf8` 在 MySQL 里是最多 3 字节的残缺实现，数学题里常见的一些符号/生僻字是 4 字节字符，用 `utf8` 会直接插入失败或者被截断/替换成乱码。建议排序规则统一用 `utf8mb4_unicode_ci`（和现有库保持一致，避免两边字符集不同将来 JOIN 时报 "Illegal mix of collations"）。

写入时用参数化查询（`?`/`%s` 占位符，或者你的技术栈里数据库驱动自带的参数绑定），不要手工拼接字符串再转义——题干 HTML 里经常出现单引号、反斜杠、换行，手工转义很容易漏。

## 3. 完整表结构（DDL）

### 3.1 `questions`——只挑出和这次任务相关的部分说明，但给出真实的完整建表语句

这是共享表的**真实完整结构**（比上一份文档 3.2 节列出的子集更完整）。**分两组**：第一组是这次任务要写的列，第二组是表里存在但**不归这次任务管**的列——之所以要把第二组也列出来，是为了让你清楚知道"这张表还有别的东西，我这次的 INSERT/UPDATE 语句不应该出现这些列名"，而不是假装它们不存在。

```sql
CREATE TABLE IF NOT EXISTS questions (
    -- ================================================================
    -- 第一组：这次任务负责的列（题干相关，约 30 列）
    -- ================================================================
    question_id       VARCHAR(64)  NOT NULL,   -- 题目 ID，主键
    grade             VARCHAR(8),               -- 学段，固定值（本项目用 "middle"）
    bank_id           VARCHAR(16),              -- 题库编号

    stem_html         MEDIUMTEXT,               -- 题干原始 HTML（已剥位置号）
    stem_text         MEDIUMTEXT,               -- 题干纯文本（已剥位置号）
    stem_status       VARCHAR(16) DEFAULT 'none', -- 'html_saved' / 'none'
    stem_hash         VARCHAR(32),              -- stem_html 的 md5，判重用

    qtype             VARCHAR(32),
    qtype_code        VARCHAR(16),
    qtype_full        VARCHAR(32),
    qtype_sub         VARCHAR(16),

    difficulty        VARCHAR(16),
    difficulty_code   VARCHAR(8),
    difficulty_band   VARCHAR(8),
    score_rate        DOUBLE,

    source            TEXT,
    title_abbr        VARCHAR(128),
    category_id       VARCHAR(16),
    category_name     VARCHAR(64),

    school_year       VARCHAR(16),
    year              INT,
    grade_level       VARCHAR(16),
    term              VARCHAR(16),
    province          VARCHAR(16),
    province_code     VARCHAR(8),
    city              VARCHAR(32),
    source_type       VARCHAR(32),

    paper_id          VARCHAR(32),
    used_count        INT,
    is_famous_school  TINYINT,
    is_real_exam      TINYINT,

    list_url          TEXT,
    knowledge_id      VARCHAR(32),              -- 第一个知识点的 ID（主知识点）
    knowledge_tags    TEXT,                     -- 全部知识点名称，JSON 数组字符串

    raw_day           VARCHAR(10),              -- 写入时的日期 YYYY-MM-DD，自动填
    first_seen_at     VARCHAR(32),              -- 第一次插入这道题的时间戳，自动填，之后不再改

    -- ================================================================
    -- 第二组：其它阶段专属的列 —— ★不要在这次任务的 INSERT/UPDATE 里出现★
    -- 只是把真实表结构如实列出来，避免你以为这张表只有上面那些列
    -- ================================================================
    stem_md               MEDIUMTEXT,           -- 离线渲染阶段产物
    stem_at                VARCHAR(32),          -- 离线渲染阶段写入的时间戳
    render_status          VARCHAR(16),
    stem_html_local        MEDIUMTEXT,
    stem_body_html         MEDIUMTEXT,
    stem_body_html_local   MEDIUMTEXT,
    stem_body_md           MEDIUMTEXT,
    stem_body_text         MEDIUMTEXT,
    options_html           MEDIUMTEXT,
    options_html_local     MEDIUMTEXT,
    options_md             MEDIUMTEXT,
    options_text           MEDIUMTEXT,
    blank_count             INT,
    sub_question_cnt        INT,
    option_count             INT,
    orig_no                  VARCHAR(16),        -- 遗留列，当前未使用，忽略即可

    answer_img         TEXT,                    -- 答案抓取阶段
    answer_md           MEDIUMTEXT,
    answer_status        VARCHAR(16) DEFAULT 'none',
    answer_at             VARCHAR(32),

    PRIMARY KEY (question_id),
    KEY idx_q_answer    (answer_status),
    KEY idx_q_knowledge (knowledge_id, qtype, difficulty),
    KEY idx_q_source    (source_type, grade_level, term),
    KEY idx_q_area      (province_code, city),
    KEY idx_q_band      (difficulty_band, score_rate),
    KEY idx_q_paper     (paper_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

### 3.2 `question_knowledge`——完全归这次任务管

```sql
CREATE TABLE IF NOT EXISTS question_knowledge (
    question_id     VARCHAR(64)  NOT NULL,
    knowledge_id    VARCHAR(32)  NOT NULL,

    knowledge_name  VARCHAR(128),
    ord             INT DEFAULT 0,

    PRIMARY KEY (question_id, knowledge_id),
    KEY idx_qk_knowledge (knowledge_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

### 3.3 `question_sources`——完全归这次任务管

```sql
CREATE TABLE IF NOT EXISTS question_sources (
    question_id     VARCHAR(64)  NOT NULL,
    paper_id        VARCHAR(32)  NOT NULL,

    paper_title     TEXT,
    ord             INT DEFAULT 0,

    PRIMARY KEY (question_id, paper_id),
    KEY idx_qs_paper (paper_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

## 5. 写入逻辑

### 5.1 先判断，再决定写不写

```
拿到一道题的解析字典 rec：

existing = SELECT bank_id, stem_status, answer_status, answer_img, stem_hash, render_status
           FROM questions WHERE question_id = rec.question_id
           # 只查这几列就够，不用 SELECT * 把整行大字段都读回来

如果 existing 存在，且 existing.stem_hash 非空：
    → 跳过，这道题这次什么都不写（题干和其它字段都不动）
    # 已经有可用的题干了，不需要重新解析/重新写。
    # 判据用 stem_hash 而不是重新读一遍完整 stem_html 再判断是否为空——
    # 两者等价（stem_hash 就是从 stem_html 算出来的），但只查短字段更省。

否则（这道题库里没有，或者库里有但题干是空的半成品）：
    → 走 5.2 节的插入/更新流程
```

**★ 已存在且题干非空时，不要用新抓到的内容去"更新"这一行**——即使这次抓到的内容和库里的看起来不完全一样（比如 `list_url` 不同），也不要更新。原因见《题干解析规范.md》第 5 节：`stem_html` 剥过位置号之后内容本身应该是稳定的，如果还看到差异，大概率是因为其它抓取上下文（页码、知识点）不同导致的噪音，拿它做比对更新没有意义，还会白白产生大量写操作。

### 5.2 插入 / 更新

```
row = 按第 4.1 节的映射表，把 rec 转成 {列名: 值} 的字典
      （值是空的 key 直接不放进这个字典，不要显式设 NULL）

如果 existing 不存在（全新的题）：
    row.first_seen_at = 当前时间戳
    row.raw_day = 今天的日期
    执行：INSERT INTO questions (row 的全部列) VALUES (row 的全部值)
    如果插入时报主键冲突（极少见的并发场景，两个抓取进程同时抓到同一题）：
        当作"已存在"处理，走下面的更新分支重新来一次

否则（existing 存在但题干是空的半成品）：
    row.raw_day = 今天的日期
    # ★ 不要设 row.first_seen_at —— 那个字段只在第一次插入时写一次，
    #   后续任何更新都不应该改它，改了就丢失了"这道题最早是什么时候见到的"这个信息
    执行：UPDATE questions SET <row 里每个 key> = <对应的值>, ...
          WHERE question_id = rec.question_id
    # ★★★ 这一条 UPDATE 语句里 SET 的列，必须严格等于 row 字典里出现的 key，
    #     一个不多一个不少。绝对不能写成"把 questions 表全部列都摆进 SET 子句、
    #     没解析到的填 NULL"——那样会把 answer_img / answer_status /
    #     stem_md / render_status 这些其它阶段已经写好的数据全部冲成 NULL，
    #     等于把已经抓到的答案数据销毁掉。这是这次任务里唯一一条"做错了
    #     会造成不可逆数据损失"的规则，务必用参数化/按字段名逐个 SET 的方式写，
    #     不要图方便用"整行覆盖"式的写法。
```

### 5.3 两张关联表：先删后插

```
写完 questions 之后（不管是插入还是更新分支）：

DELETE FROM question_knowledge WHERE question_id = rec.question_id
for i, k in enumerate(rec.knowledge):
    如果 k.id 是空的：跳过这一条
    INSERT INTO question_knowledge (question_id, knowledge_id, knowledge_name, ord)
    VALUES (rec.question_id, k.id, k.name, i)

DELETE FROM question_sources WHERE question_id = rec.question_id
for i, s in enumerate(rec.sources):
    如果 s.paper_id 是空的：跳过这一条
    INSERT INTO question_sources (question_id, paper_id, paper_title, ord)
    VALUES (rec.question_id, s.paper_id, s.title, i)
```

**为什么是"先删这道题的旧关联再全部重插"，而不是"只插入新的/只更新差异"**：这两张表的内容完全由这一次解析结果决定，没有"部分更新"的需求——重新解析一遍，关联关系就应该是重新解析出来的这一份，不存在"库里有一条关联但这次解析没抓到，要不要保留"这种情况需要判断。先删后插实现最简单，也不会有残留的旧数据。

（第 5.1 节已经说明：题干非空的题这次直接跳过，不会走到这一步——所以这两张关联表实际上只在"全新的题"和"补半成品"这两种情况下才会被重写，不会对已经处理过的题反复删了又插。）

### 5.4 提交粒度

一道题涉及的三处写入——`questions` 的 INSERT/UPDATE、`question_knowledge` 的删+插、`question_sources` 的删+插——应该作为**一批**一起提交（比如放在同一个数据库事务里，或者至少确保三处都执行完再统一 commit）。不要拆成三次独立提交，否则程序中途崩溃（网络断开、进程被杀）时可能出现"`questions` 表已经有这一行，但两张关联表还是空的"这种不一致状态，而且不会有任何报错提示你这件事发生了。

## 7. 严禁事项清单

1. **不要写覆盖全表的 UPDATE**——`UPDATE questions SET col1=?, col2=?, ..., col60=? WHERE question_id=?` 这种把没解析到的列也显式设进 SET 子句（哪怕设成 NULL）的写法，会销毁其它阶段已经写好的数据。只 SET 这次任务解析出来的、且值非空的那些列。
2. **不要更新已经有非空 `stem_html` 的题**——第 5.1 节的判断必须先做，不能"反正都要写，覆盖一下也无所谓"。
3. **不要往下面这些列写任何东西**（哪怕是留空/NULL，也不要让它们出现在 INSERT 的列清单或 UPDATE 的 SET 子句里）：`stem_md`、`stem_at`、`render_status`、`stem_html_local`、`stem_body_html`、`stem_body_html_local`、`stem_body_md`、`stem_body_text`、`options_html`、`options_html_local`、`options_md`、`options_text`、`blank_count`、`sub_question_cnt`、`option_count`、`orig_no`、`answer_img`、`answer_md`、`answer_status`、`answer_at`。这些是其它阶段的产物列。
4. **不要在插入之外的场景改写 `first_seen_at`**——它的语义是"第一次见到这道题的时间"，只在 INSERT 时写一次。
5. **`question_knowledge`/`question_sources` 要用"先删这道题的旧关联再全部重插"**，不要只插不删（会残留旧关联），也不要试图做"差异更新"（没必要，也容易出错）。
6. **一道题的三处写入要一起提交**，不要拆成独立的、互不关联的多次提交。

## 8. 范围重申

这份文档到"题干写入数据库"为止。答案抓取、离线 HTML→Markdown 转换、图片下载/OCR/本地化、选项拆分入 `question_options` 这些阶段各自有自己的写入逻辑，都会往 `questions` 这张共享表补上属于它们自己的那些列——这份文档定义的写入逻辑执行完之后，这道题在库里应该处于"题干齐全、其它阶段的列保持原样不受影响"的状态，后续阶段会在这个基础上继续补全，不需要这次任务关心。
